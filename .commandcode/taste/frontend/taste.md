# Taste — frontend

- Likes numeric quantity/stock values displayed cleanly in tables: no fixed-decimal trailing zeros rendered as strings (e.g. "5.0000" from a `decimal:4` cast), no floating-point artifacts (e.g. "4.999999999"), and thousand separators per locale (id-ID). The fix is expected on both sides: backend casts send clean floats, and frontend formats via a helper that rounds to a reasonable precision and strips trailing zeros. When such odd numeric formatting appears, the user asks what the underlying type is (decimal vs integer) and expects it resolved at the display layer. Confidence: 0.6

- Wants list pages to offer a read-only **Detail** modal (per-row button) showing the record's full header info plus its line items, and expects the same detail-modal pattern to be applied consistently to every related page in a module (e.g. Purchase Return and Stock Opname both received identical Detail modals with a header summary grid + items table). When told to "add detail here" on one page, the user expects corresponding pages to follow the same structure. Confidence: 0.7

- Displays dates in the grid/detail UI as localized Indonesian day-name + date ("Senin, 2026-09-09"), tolerant of both date-only and full datetime input, via a shared `formatDate` helper. Confidence: 0.6

- Cares about input focus stability in forms: reports when typing in a field makes the cursor jump to another field, expecting the cause to be fixed rather than working around it. Root cause is a React anti-pattern — defining a component (e.g., the `Section` helper) inside the render function so a new function identity is created each render, which makes React unmount/remount the whole subtree and lose focus; fix is to hoist the helper component to module scope so inputs aren't remounted on every keystroke. Confidence: 0.5

- When asked to add a supplementary charge to a business document (e.g., "tambah ongkos kirim" on a PO), expects it be a real, functional feature: a new DB column, a backend endpoint, and a control in the detail modal whose saved value ("langsung bertambah") immediately recomputes the displayed total from the API response without a page refresh. Wants the detail view to show a transparent total composition (line subtotal → charge (e.g. shipping cost) → grand total), and wants printed documents kept consistent with the on-screen totals. Confidence: 0.5

- Wants forms (e.g. add/edit modals) to be proportional and informative: fields grouped into clearly-labeled sections/cards by purpose (e.g. Informasi Umum / Informasi Keuangan / Alamat / Kontak), every section with a short hint explaining what to fill, placeholder examples on inputs ("cth: ..."), required fields marked with `*` and validated, and descriptive option labels (e.g. "B2B — Perusahaan") rather than bare values. Confidence: 0.7

- Wants sidebar/navigation route active-state matching to be per-segment (e.g. `pathname === path || pathname.startsWith(path + '/')`) rather than a bare `startsWith(path)` prefix check, so sibling routes that share a string prefix (e.g. `/product` vs `/production`) don't highlight/collapse the wrong menu. The user reported the Production menu opening the Product child as a bug, and the fix was applied consistently across accordion init, navigation effect, and parent highlight. Confidence: 0.5

- Treats role/permission configuration as something that must actually govern the UI, not just exist in config: users with different roles seeing the identical sidebar after login is reported as a bug to fix ("saat ini semua user dengan roles berbeda tampil menu yang sama semua"). Expects menus (and report tabs/printable documents) shown to a user to be scoped to that user's role/permissions from the backend login response, so a role's effective permissions determine what appears after re-login. Confidence: 0.5
